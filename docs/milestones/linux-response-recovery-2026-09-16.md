# Linux 无回复排查与修复（2026-09-16）

## 已确认原因

1. 北京时间 00:10:19，一条 QQ 回复在原始 60 秒预算只剩约 12 毫秒时开始发送。QQ 已实际交付，但 ACK 等待超时，发送记录成为缺少消息 ID 的 `unknown`。旧实现只恢复带 ID 的记录，因此该未知交付持续阻止所有新的自动发送，重启也无法解除。
2. 08:40 主机重启后，独立 NapCat 账号未自动登录，OneBot 6301 未监听。QQDirect 新鲜心跳仍在更新，但 `connected=false`；其 systemd 启动检查持续等待连接。操作员扫码后已确认正确账号重新登录。
3. 同期日报在 Runtime 顺序心跳处理里等待整个聚合；数据库、trace 和目录读取也同步占用事件循环。监控总览反序列化全部事件，并重复携带最多 720 个完整运行状态，增加响应开销。这些是独立确认的阻塞风险，不作为上述 QQ 故障的推测替代。

## 修复

- 保留原始 deadline，发送前至少留 2 秒预算，避免只剩毫秒仍产生外部副作用。
- 对缺少 ACK ID 的群发送，从原始协议证据中选择同群、同自身账号、精确正文、严格时间窗口内唯一的实时回声，并再用独立协议读取核验；成功后补记原生回执。证据不充分仍保持未知，不重发或续发旧消息。
- QQ 桥重启后 `get_msg` 缓存丢失时，允许有界群历史核对；仍须匹配唯一消息 ID、群、本人和正文。
- systemd boot-only 检查改为校验当前 PID、release 和新鲜心跳，允许等待扫码；普通健康检查仍要求连接成功。增加脱敏断线/恢复日志。
- 日报归档在单实例后台任务运行，阻塞 I/O 放入工作线程；关闭时先收尾再释放存储。
- 监控总览使用 SQL 统计并返回紧凑采样；资源采样复用进程 CPU 基线，并检测退出与 PID 重用。
