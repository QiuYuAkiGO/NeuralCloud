## 2. G0：先做实际进度同步

### G0-A：只读定位实际运行实例

通过用户已授权的连接方式定位真正运行 Misty 的 Linux 机器。没有连接时，停止 G0；不要临时猜测 IP、使用陌生机器或将另一个副本视为同一实例。

需要确定两项目是否实际安装/启用；不能因仓库存在就假定服务正在运行。分别检查：

- 服务账户、systemd/容器/其他真实启动入口、工作目录、进程及模块加载位置。
- 实际仓库、分支、HEAD、子模块、工作树、未提交修改和未跟踪源文件。
- 虚拟环境、Python/Node、依赖锁文件、实际安装版本、容器镜像摘要与挂载关系。
- 数据目录、日志目录、插件资料目录，以及生产写入者和自主入口。
- 当前功能的实现、启用和验收状况，三者分开记录。

操作提示（仅在已经定位的正确仓库中只读执行，不是自动执行脚本）：

```text
git rev-parse --show-toplevel
git rev-parse HEAD
git status --porcelain=v1 --untracked-files=all
git diff --stat
git diff --cached --stat
git ls-files --others --exclude-standard
```

完整 diff、进程命令行、环境和部署文件可能包含密钥；在受限维护区保存、脱敏，不直接打印进公开日志或提交到 Git。不得读取或上传不相关个人目录。不要通过自动运行仓库模块来“检查版本”，以免 import 触发真实副作用。

磁盘代码与内存中已加载代码不一致时，记录文件 hash、进程启动时间、部署来源及不确定部分，不为了使其一致立即重启。正在运行的 wheel、镜像、动态挂载及源码必须能形成可解释的对应关系。

### G0-B：完整保存远端改动

在生产目录之外的受限位置建立带时间和实例标识的源码快照。覆盖 tracked 修改、staged 修改、untracked 源码、构建/依赖/服务配置等必要内容。不能只记录 HEAD 或只保存 git diff 而遗漏未跟踪文件。

敏感配置、Token、账号 cookie、聊天记录、记忆数据、浏览器资料和密钥不得进入 Git。需要恢复的私有内容单独加密保存，Git 中只保存脱敏模板和“已单独保全”状态，不保存秘密内容或可被字典推断的秘密摘要。

快照记录：稳定快照 ID、采集时间、源码文件清单及 hash、原 HEAD、改动统计、排除项、部署对应关系、恢复方法。若远端无可用 Git 历史，也先建立真实源快照，不把 GitHub 文件补入后声称那就是远端现状。

### G0-C：同步到版本控制与进度记录

以远端实际源码构建隔离的同步分支/工作区，保留已有历史，提交可追溯的服务器直接修改。同步提交与重构提交严格分开；不强推覆盖他人提交，不合并旧代码覆盖生产目录。

NeuralCloud 和 MistyAI 分别产生同步基线提交，或者在确无差异时提供已核对一致的证据。对不能进入 Git 的差异做明确清单；“源码一致”比较的是纳入基线的实际源码文件，不以排除秘密为由掩盖功能改动。

历史 GitHub 有而远端没有的修复，只记录差异，不能不经核实直接套用；远端有而 GitHub 没有的功能不能被当作未实现重新覆盖。完成同步后，重新校正本方案的模块路径和已实现进度，保留用户已确认的目标边界。

本方案分支只作为文档来源；实际实施分支从同步后的基线建立。可以 cherry-pick 文档提交，不能把方案分支的完整旧代码树作为部署输入。

### G0-E：通过条件

以下全部满足才能开始实质改造：实际运行位置明确；两仓库直接改动已保存；基线提交与实际源码映射清楚；部署和数据清单齐全；进度报告发布；没有影响实施依据的未解释差异。

## 3. 无人值守执行约定

### 3.1 默认继续与默认暂停

| 情形 | 处理 |
|---|---|
| 产品规则已确认 | 直接按 v1.0 实施，不再询问 |
| 普通可逆实现选择 | 选低维护成本方案，记录理由，隔离测试 |
| G0 通过后的开发 | 在隔离工作区小步提交，保持生产代码不被工作树试验覆盖 |
| 可重试的暂时失败 | 有限重试、退避、保留错误与游标；不得无限循环 |
| 远端基线不清楚 | 阻塞代码改造，不以 GitHub 猜测代替 |
| 冷仓库未配置或不可达 | 可做合成数据测试；不能剥离生产原文 |
| 外部校验或恢复失败 | 保留本地源数据，标记失败，禁止继续删除 |
| 需要敏感授权但用户睡觉 | 持久等待，一次请求加去重；无回复不批准 |
| 真实模型/渠道不可用 | 报告未验证，不用 mock 成功冒充实机 |
| 用户要求停止/出现紧急情况 | 在安全点收敛，不重发未知副作用 |

实施目标中的停机迁移已获方向性确认，不需要为每次普通代码编辑重新申请；正式操作仍须满足实例、数据恢复点、授权配置和切换门禁。不能把“无人干预”扩大成随意上传冷数据、安装系统软件或扩大外部账号权限。

### 3.2 状态、预算与中断恢复

每个任务保留 `NOT_STARTED / RUNNING / PASSED / FAILED / BLOCKED / SKIPPED_WITH_REASON`、baseline ID、输入版本、输出提交、真实测试命令与退出码、checkpoint、恢复点、下一步和阻塞原因。

对耗时任务设置 CPU/IO/磁盘/模型调用预算和重试上限；已有明确配置优先，没有配置时采取受控保守值并记录，不开通付费新服务、不无限增加资源来绕过故障。

进程/实施 Agent 中断后，先核对 checkpoint、Git 状态、真实写入者和外部回执，再续跑。不要从头重新停机、发送消息、执行审批或导入全部记忆。

允许并行开发已解除依赖的模块，但同一生产实例、数据库迁移、归档批次和角色动力发布必须有明确唯一所有者。并行会话不能各自启动一份正常 Misty。

### 3.3 汇报方式

每个工作包结束生成简短的阶段报告，结果和失败都保留。需要用户决定的事项合并成最小阻塞清单；不在用户睡眠期间反复问同一个问题，不假装可以绕过。

除已经配置的用户审批/运维通道外，不向真实群聊发送测试进度。自动进度文件是持久记录，不宣称有不存在的后台通知服务。

## 4. 生产数据和冷剥离的独立门禁

冷记忆位于服务器之外，日常角色没有凭据、挂载、工具入口或自动回源路径。服务器本地归档子目录不能冒充已经离机。

本地剥离必须同时具备：批准的目标和范围、源 revision 冻结、外部持久保存、条数/hash/引用验证、解密及隔离恢复验证、独立恢复副本、在线依赖处理、旁路副本清单。

任何一项失败都保留本地原文；磁盘压力不能成为例外。完成前可以标“已导出/待验证/部分脱离”，不能标“归档完成且本地已清”。

旁路包括 FTS、向量 payload、热点快照、Harness 会话、插件历史、旧 JSON、日志、附件、暂存包和本地备份。上游日志不支持安全局部编辑时先关闭/轮换会话，不能破坏其恢复格式。

归档撤销和恢复只经管理面。Misty 想起旧事或主模型发出工具请求，不自动获得冷库读取权；全局在线记忆 B 不覆盖该限制。

## 5. 建议执行顺序

```text
G0 远端实际代码和进度同步
→ P0 真实启动/容量测量与插件契约验证
→ P1 在线持久层、离线归档和迁移器
→ P2 常驻全局记忆服务与插件
→ P3 内稳态/动力与 P4 情绪/权限接线
→ P5 实际 QQ + 视频内容理解纵切
→ P6 停机迁移、回滚演练、切换与退役
```

只在明确依赖已满足时并行。新旧数据差异不明、存在双写、真实回执不可验证或冷恢复失败时，不自动推进到生产切换。

测试证据和代码提交分开：文件存在不是测试通过，mock 测试不是实机，服务 active 不是场景闭环，构建成功不是已经部署，压缩成功不是数据已经安全离机。
