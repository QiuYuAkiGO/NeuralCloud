# QQ 按需 Kimi 识图发布（2026-10-06）

本次按用户确认保留主模型 `qwen3.8-27b`，恢复 QQ 图片获取，并让主模型自行决定是否调用 `kimi-k2.6` 非思考识图工具。Kimi 返回图片观察，最终人格回复仍由原主模型生成。用户同时授权提交全部现有项目改动；凭据、运行数据库、私人 QQ 报告和个人目录不入库。

## 实现与配置

- Direct：`qq_image_mode=all`、`qq_image_analysis=on_demand`。入口只下载、校验和保存图片，不预先调用视觉模型。
- Cognitive：主模型填写可选 `vision_request`，每轮最多调用一次、最多四张。Kimi 使用官方中国区接口、非思考模式和温度 0.6；凭据通过 `NC_QQ_VISION_TOOL_CONFIG` 独立配置。
- 识图结果交回主模型，再由它选择是否生成 `web_plan`。Runtime 使用现有搜索授权和来源检查；`qq_web_policy=after_gate` 对现有可发送会话启用，QQ 发送名单不变。
- 超时、无效来源、哈希变化或模型结果截断不会形成确定图片事实；冻结检查点支持恢复、撤销和重放，不重复付费识图。

配置模板与操作说明见 [QQ 按需识图](../QQ_ON_DEMAND_VISION.md)。先前本地视觉、Kimi 与 DeepSeek 的直接回复对比见 [模型评测](../research/qq-vision-local-api-comparison-20261006.md)；直接回复的耗时不等于本次工具链路耗时。

联网样本使用常规 WebController 和真实 Tavily provider，隔离了授权上下文与调用记录；Runtime 的来源/授权编排由关联回归覆盖。搜索返回五个页面摘要，并非五个官方来源，也没有读取原图反向检索。没有把摘要命中当作像素身份的独立证明。没有向实际 QQ 会话投递测试消息。

本批样本验证了“可以选择调用、也可以不调用”的接线。它不证明模型会在每次知识不足时都主动搜索，也不是线上自然会话的 P95。角色换装识别仍需要观察，保留候选不确定性比凭外观硬补名称更合适。

## 回归验证

Linux 完整主套件共 7,756 项：7,241 passed、499 skipped、16 failed，471.73 秒。16 项失败来自三个旧测试文件：直接调用 Runtime 内部处理器的夹具缺少 RUNNING 状态，重放夹具把 critical 状态误当普通更新，以及共享人格夹具未提供当前字段。

随后只更新这些测试夹具，保留生产状态校验，并补充 critical 状态禁止重放发送的回归。Linux 关联回归 242 passed，17.77 秒，覆盖所有原失败项、识图、准备/恢复、搜索、计量、后台队列和 Direct。另有独立 Web 烟雾工具关闭临时数据库过早的问题，已修复并加测试；这是验收工具问题，没有改动生产 WebController。

补入下述 ID 碰撞修复后，重新完整运行 `tests`：6,989 passed、499 skipped、1 failed，477.00 秒；独立完整运行 `eval`：274 passed，45.16 秒。剩余失败为 Board 测试用固定 0.25 秒睡眠假定后台提交已结束，在并行负载下尚未结束。仅把测试改为有 3 秒上限的实际任务等待，不放宽生产命令截止时间；最终 Linux 关联回归 75 passed，9.88 秒，覆盖全部四种截止时间场景、ID/日志恢复与识图。最终验收采用完整运行与修复后的关联回归，不宣称最后重新完整跑出一次全绿结果。

Windows 的最终识图测试 21 passed，夹具修复测试 38 passed；此前扩展回归 361 passed、2 skipped，主回复链路回归 174 passed。套件存在重叠，不相加当独立总数。变更 Python 文件 Ruff 通过。

## Linux 发布

运行包版本为 `20261006-qq-vision-kimi-on-demand-v2`，424 个文件；归档 SHA-256：`38e25dca28e30480f3f5d8db16c94f7c9c32b4a8a2317c3d256665ed204d004b`。保留上一可用版本 `20261006-background-queues-v2`，配置备份位于 `/var/backups/neuralcloud/20261006-qq-vision-kimi-on-demand-config`。本次不改数据库结构，不恢复旧数据覆盖新状态。

首版启动暴露了旧命令 ID 的随机碰撞：9 月 15 日与 10 月 6 日的两条心跳命令使用了同一 32 位 ID，事件、请求哈希和提交修订均不同。旧贡献对象的不可变检查阻止了恢复；此前这次漏记也使 Runtime 的快照落后，下一心跳因修订冲突暂停。新版本把持久 ID 的随机部分扩大至 128 位，恢复时按幂等键、历史先后和完整请求哈希匹配命令。历史碰撞的第二条贡献单独以请求哈希绑定，第一条原对象保持不变；同一事件的不同内容仍拒绝覆盖。

新增回归覆盖完整/增量恢复、缺少日志幂等键的旧记录、重复重放及真正内容冲突，Windows 相关测试 50 passed。Linux 真实状态的隔离副本从 118,485 条贡献恢复到 118,486 条，再次重放没有新增审计行，完整审计链通过。生产原数据库未被副本验证修改，原始 journal 未删改。首版退出时重新抛出已知启动异常，取消启动等待后确认进程全部退出；后续启动依然执行正常恢复和健康检查。

发布已完成，六个业务服务均为 active/running，Runtime 为 RUNNING、健康检查无降级，未完成命令和动作均为零；QQ 已连接并启用自动回复。首次最终状态读取在启动回填期间超过 5 秒，随后重新读取确认健康，没有因此重复重启服务。服务账号可读取权限为 `0600` 的私有 Kimi 配置；使用最终发布代码实测 OCR 回复 8.381 秒、一次识图，“不用看图”对照 2.464 秒、零识图。
