# Qwen / DeepSeek：冻结人设与前后提示词对照

2026-10-05，按用户确认的 **人民币 1 元预算**完成 80 次真实接口调用，其中 DeepSeek 40 次、Qwen 40 次。**当前样本支持继续使用 DeepSeek 作为主回复模型：完整回复更快，普通聊天篇幅更稳定。Qwen3.8-27B 能承担本地生成和短输入 goal 决策，但本轮没有显示出替换 DeepSeek 的整体质量优势。**

本次保守费用记录为 **0.41 元**：按官方高峰费率计算，并把每个付费请求向上取整到分。依据接口回传 token 用量，不逐次取整的高峰费率估算为 **0.064891 元**；这不是账单实扣值。其他会话共用 API Key，因此没有把账户余额变化归因到本轮。Qwen 的外部 API 费用为 0，GPU 电费未计。

## 完整正文生成

所有 80 次接口调用均为 HTTP 200，无可见思考输出。HTTP 成功不代表有可发送正文：Qwen 修改后组中一次称赞回应只返回 `[END]`，解析后为空，保留为失败样例。

| 模型 | 提示词 | 样本数 | 完整耗时中位数 | 本批样本 P95 | 可见非空正文 | 普通样例超过 60 字符 | 普通样例超过 2 个标点句 |
|---|---|---:|---:|---:|---:|---:|---:|
| DeepSeek | 修改前 | 16 | 0.665 秒 | 0.836 秒 | 16/16 | 0/14 | 0/14 |
| DeepSeek | 修改后 | 16 | 0.765 秒 | 1.055 秒 | 16/16 | 0/14 | 1/14 |
| Qwen3.8-27B | 修改前 | 16 | 1.206 秒 | 2.259 秒 | 16/16 | 2/14 | 5/14 |
| Qwen3.8-27B | 修改后 | 16 | 1.149 秒 | 1.875 秒 | 15/16 | 3/14 | 5/14 |

时间从 HTTP 分发到完整读取，未清空服务端缓存，是本批观察值。16 条样本的 P95 不能作为生产 SLA。`expanded` 场景的两条输出不进入普通篇幅统计；60 字符/2 句只是统一的描述性观察线，修改后提示词允许依内容自然展开，不能把这些计数直接当作违约或整体质量分数。字符计数不含空白；句数按标点分割，不是人工语义断句。

显示正文使用冻结项目的协议解析器隐藏 `[END]` / `[CONTINUE]`；没有重写内容或补调空回复。`report.json` 内初始 `evaluation.usable` 仅检查原始响应，可能把单独 `[END]` 当作原始非空文本；**正文可用性以 `normalized-results.json` 与上表为准**。

## 内容观察

以下是对全部 64 条正文的非盲阅读观察，没有独立人工评分或付费模型裁判，因此不发布总质量分数。

- **未知往事**：DeepSeek 修改前两次均先说明缺少记录，修改后两次直接询问争吵起因。Qwen 修改后仍保留“我好像没对上号”的开头。两者都没有编造争吵原因；在固定人格下，DeepSeek 更一致地采用了新提示词的直接澄清方式。
- **直接选择**：两者都选安静键盘。Qwen 修改前加了较长理由，修改后一次只给选择，另一次给短理由；变化方向与减少解释的意图一致。
- **动机判断**：两者都认为“想被看见”可能比“争第一”更贴近当前感受。Qwen 修改前一次写成三段、包含自我提问步骤，修改后另一次仍有多行解释和“这样想会不会舒服一点”的引导式结尾；DeepSeek 四次均更简短。
- **称赞**：DeepSeek 四次都承接“听懂了”；Qwen 修改前回复简短，修改后一次为“那就好”，另一次只有结束标记，没有承接正文。
- **自嘲玩笑**：两者都抓住“给计划表改颜色”，也都有轻度鼓励倾向，尚不能由两次生成判断谁更自然。
- **详细解释**：两者大体给出社会比较的定义和例子。Qwen 修改前一次追加音乐推荐的第一人称类比，概念关联较弱；修改后两次集中到相机/成绩或旅行比较。DeepSeek 修改后一次偏短、另一次展开较充分，也有生成差异。

普通输出长度中位数均下降：DeepSeek 30→22.5 字符，Qwen 42→29 字符；Qwen 的长回复和多句尾部仍存在，不能把中位数下降理解为每个场景都更简短。

## SSE 与 goal

SSE 仅“选择”和“展开”各一次、每版每模型两条。Qwen 首字范围 0.202–1.149 秒，DeepSeek 0.425–0.664 秒；Qwen 修改前缓存下首字较快，修改后首个新提示词的选择请求较慢。样本太少，不给稳定的流式优劣排名。现有 NeuralCloud 正文客户端仍是非流式，主表的完整耗时更接近当前生成阶段。

| goal 模型 | 语义与契约通过 | API 耗时范围 | 中位数 |
|---|---:|---:|---:|
| DeepSeek | 4/4 | 0.596–1.417 秒 | 1.088 秒 |
| Qwen3.8-27B | 4/4 | 1.669–6.141 秒 | 2.216 秒 |

四个合成状态为无机会等待、提出活动、未完成步骤不得完成、独立保存回执支持完成。使用相同 `json_object` 模式，按冻结 `GoalChoice`、episode 证据规则和 offer 参数检查原始返回；这部分隔离比较模型，不走 DeepSeek 新增的 Responses Schema 传输路线，也不执行真实 Runtime 命令。耗时指 API 完整读取，校验在返回后进行；两组都明显低于当前 25 秒模型预算。这不能代替长期 goal 活动验收。

## 预算、恢复与证据

每次 DeepSeek 请求在发送前持久化槽位与最坏费用预留；失败或中断的不确定槽位占预算且不重试。根据返回 usage 释放多余预留。调用次序固定随机化，配对模型先后顺序交替；两模型均串行测量。

执行在第 34 个槽位后遇到 Windows 文件读取共享造成的报告替换错误。加入文件替换重试后从剩余槽位继续，没有重复任何 API 请求；原/新 runner 哈希和恢复前报告均保留。80 个槽位唯一、40 对 messages 哈希一致；预算计算与文件锁处理的 4 项离线测试、Ruff 通过。
