# MistyAI / NeuralCloud：代码瘦身与错误处理收敛需求

- 状态：需求基线 / 待逐项实施（RFC）
- 日期：2026-11-14
- 范围：MistyAI、NeuralCloud 及两者与 DeepSeek Harness 的接口
- 目标基线：两个仓库的 codex/misty-harness-implementation-20261025 分支
- 本次提交性质：**仅记录需求与初步静态审计，不修改运行代码，不代表生产验收通过**

## 1. 背景与核心立场

当前架构正从历史上的多职责系统拆分为 MistyAI 常驻状态服务、NeuralCloud 独立记忆服务和 Harness 代理执行/工具编排。经过多轮迭代，部分防御性编程、静默回退、重复封装以及新旧路径共存，可能使真实错误被“正常返回”掩盖，同时增加代码理解、问题定位与后续修改成本。

**长期原则：非必要不引入防御性编程。让应该失败的操作明确失败，不以更多兜底分支制造表面上的健壮性。**

具体而言：
1. 对内部契约、不变量、配置和数据结构的违反，应明确失败，保留可诊断的原始原因；不应伪装成正常的空结果或成功。
2. 仅在能够识别故障类型、拥有恢复责任且恢复路径明确时捕获异常；不为“保险”而层层包装异常。
3. 对确实存在的外部故障（网络抖动、服务暂时不可达、资源短缺），可以实行有限重试、明确降级或暂停，但必须让调用者与运维知道操作未成功。
4. 安全、授权、数据完整性和事务边界不是“多余防御”。不能为缩短代码而牺牲它们。
5. 以 **职责单一、契约清晰、控制流简单、失败可观测** 作为健壮性的评判依据，而非 try/catch 或校验分支的数量。

## 2. 目标与非目标

### 目标

- 消除吞异常、无意义的统一兜底、错误类型丢失和不可追踪的静默失败。
- 减少跨层重复判断、重复重试、隐式默认值与只转发参数的冗余抽象。
- 明确 MistyAI、NeuralCloud、Harness 之间的异常归属、恢复责任与可接受降级行为。
- 逐步清理不再参与构建或执行的遗留路径，但保留审计、回滚与历史恢复能力。
- 在不破坏既有功能、安全和数据语义的条件下，使控制流与测试更容易理解。

### 非目标

- 不追求零异常捕获、零校验或按行数机械删代码。
- 不改变角色人设、内稳态行为策略、记忆召回语义、审批/发送安全约束。
- 本文档不授权生产切换、真实冷数据剥离、存量数据库迁移或删除生产服务。
- 不在缺少测试和失效模式分析时批量替换异常处理。

## 3. 错误处理与恢复判定规则

| 场景 | 期望处理 | 不允许的处理 |
| --- | --- | --- |
| 违反内部不变量、协议格式错误、实现缺陷 | 在责任边界抛出明确异常，保留原因与调用链，测试覆盖 | 捕获后返回空对象、假成功、默认值，继续运行 |
| 用户输入不合法、授权不足、审批未通过 | 返回明确的拒绝状态；不得执行受限动作 | 宽泛捕获后绕过授权、使用更宽松默认策略 |
| 短暂网络失败、超时、依赖服务临时不可用 | 仅对已确认可重试且幂等的调用有限重试；否则返回显式不可用状态 | 将所有异常统一解释成“没有记忆”“没有事件”或成功 |
| 持久化写入、回执含糊、事务一致性不可确认 | 保留待处理记录，停止有歧义的重放并请求对账 | 猜测操作成功或盲目重复执行 |
| 后台维护失败、过期清理失败 | 记录可定位原因，维护权限失效关闭，暴露维护异常 | 只吞掉异常并无限继续，令操作者误以为清理正常 |
| 资源释放、任务取消、进程退出 | 使用 finally/事务回滚/有界关闭等必要清理，并重新传播原始错误 | 为了“代码纯净”删除必要清理，或将取消视为普通业务错误 |

落地规则：

1. 默认让异常沿调用链传播到**明确的拥有者**。跨 HTTP、插件、进程、用户交互边界时，再将其转换为稳定的、可辨识的错误契约。
2. 避免裸 except、笼统 catch，以及“捕获所有异常然后返回 None/false/空列表/缓存未命中”。如果确有必要进行边界隔离，必须明确记录失败和理由。
3. 重试前证明该操作幂等、可恢复且不存在未确认副作用；对无效协议、配置错误、不可恢复的数据损坏等失败不自动重试。
4. 日志应保留操作标识、错误类别、底层原因和必要关联上下文。敏感凭证、私密记忆正文以及授权材料不得进入公开响应和普通日志。
5. 缓存或降级状态必须表明其不是权威结果；尤其不能把“检索服务故障”误判为“确认没有相关记忆”。
6. 不要求删除必要的 finally、事务回滚、资源清理、拒绝访问和 fail-closed 逻辑。代码是否删除，要由它维护的**具体不变量**决定。
7. 测试应验证失败语义，而不只是成功路径或“服务仍然运行”。

## 4. 首批静态审计候选（不是最终缺陷认定）

以下位置基于 2026-11-14 对上述开发分支的静态阅读，属于**优先复核目标**；须先补测试、确认外部契约和调用方预期，再决定是否改代码。

### NC-01 / P0：记忆检索异常与正常未命中混合

- 位置：NeuralCloud / plugins/dsh-neuralcloud/src/index.mjs，MemoryClient.recall。
- 观察：一个宽泛 catch 处理请求失败及同一 try 内的其它运行错误；中断请求之外，多种失败会落为 STALE_UNVERIFIED 或 CACHE_MISS。
- 风险：网络暂断与 JSON/协议错误、认证/权限问题、代码缺陷被归入相近结果，问题定位困难；调用方可能丢失真实原因。
- 方向：只对**预期服务不可达**允许明确的非权威降级；对于解析异常、响应契约违反、错误配置等让异常暴露。保持现有“不返回未经确认的缓存正文”的安全语义。
- 验证：分别模拟服务不可达、超时、非法 JSON、错误 HTTP 状态、调用取消与缓存过期；确认每类故障具备不同且可观察的处理结果。

### NC-02 / P0：Outbox 所有发送异常都进入重试计数

- 位置：NeuralCloud / plugins/dsh-neuralcloud/src/index.mjs，DurableOutbox.flush。
- 观察：catch 不区分请求暂时失败、格式错误和未取得符合预期的 DURABLE 回执，统一增加 attempts 并安排退避。
- 风险：协议缺陷或确定性错误被当作暂时故障重复排队，直到阻塞；真实根因没有明确传递。
- 方向：将可重试的传输类错误与契约错误分开；对回执缺失/含糊保持待处理、不可丢弃，并按现有幂等及对账要求决定能否再发送。错误状态必须可定位，不能为简化而删除事务或出站队列。
- 验证：服务超时、返回非法回执、永久拒绝、入库后连接断开、重复事件、队列重启恢复。**不得丢事件、重复制造不受控副作用或将未确认写入报成成功。**

### MA-01 / P1：内稳态后台定时任务的故障可观测性

- 位置：MistyAI / src/mistyai/integration/service.py，ticks。
- 观察：对 sqlite3.Error / Refusal 最多累计三次，之后设置统称 BLOCKED_STORAGE_OR_POLICY；错误细节未随状态保留。非这些类型的异常则可能直接使任务异常退出。
- 风险：操作者无法通过当前状态准确区分存储故障与策略拒绝，也不容易判断后台循环是否非预期停止。
- 方向：保留明确的有限失败策略，但为管理侧记录最近失败类型/原因与时间；让异常任务退出可被发现。不要将所有内部错误转成可忽略状态，也不必为不同异常叠加多层防御。
- 验证：数据库不可写、策略拒绝、意外异常、任务取消、重启；确保健康状态不会误报正常运行。

### NC-03 / P1：临时归档视图的清理循环

- 位置：NeuralCloud / src/neuralcloud/temporary_views.py，后台 reap/sweep。
- 观察：周期清理捕获 Exception 后仅保存异常类名；需确认故障升级、人工处理及过期访问保护是否充分。
- 风险：连续失败的原因不清晰，维护异常可能长期潜伏。
- 方向：保留视图过期、撤销、加密副本和授权域的 fail-closed 约束；补足管理可观测性，定义何时暂停或升级故障。不要机械删除为确保清理/撤销执行并重新抛错而存在的 BaseException 清理代码。
- 验证：权限异常、文件损坏、清理受阻、并发关闭、重启撤销；过期或被撤销视图不得继续暴露数据。

### BOTH-01 / P2：新旧实现共存与重复抽象

- 位置：仓库历史模块、旧 Harness/GUI/语音/身体集成路径、打包与测试配置，以及新增适配层。
- 观察：当前 README 明确说明部分遗留模块已从新的默认包/测试路径排除，但原始源码仍为恢复而保留。
- 方向：先绘制“实际运行入口 → 依赖 → 构建产物 → 测试 → 生产调用”的可达性图。证明已无引用且可从 Git 历史恢复后，才能决定归档或删除。优先消除职责重复、接口旁路和只用于吞错的多余包装。
- 验证：所有活跃入口、部署脚本、Android/MCP 接入、回滚路径与迁移工具都经过检查；不得仅凭模块名称或大小进行删除。

## 5. 职责边界与统一规则

- **MistyAI**：拥有角色当前状态、内稳态/活动、行动机会、审批与投递账本；负责清晰表明状态更新、审批和发送决策的结果。不能替 NeuralCloud 猜测记忆写入成功。
- **NeuralCloud**：拥有记忆持久化、检索、修订失效、归档、临时授权视图；负责提供权威/非权威结果区分和持久化错误语义。不能替 Harness 吞掉调用错误并伪装为“没有记忆”。
- **DeepSeek Harness 与插件边界**：拥有 Agent 运行、工具编排及显式重试/降级决策；针对外部能力只采用约定的错误契约，不为同一个操作叠加跨层重复重试。
- **调用方与运维**：应能够回答“操作是否成功、是否可重试、是否已有副作用、何时需要人工介入”，而不是只能看到“空响应”。

## 6. 实施顺序与交付要求

### P0：建立基线与故障分类（先做）

1. 固定目标提交与运行入口，记录现有测试结果及外部协议；列出当前实际生产与隔离验证的差异。
2. 搜索并审计所有宽泛异常捕获、静默默认值、重复 retry、隐式状态转换和未使用包装层；每一处标记：必须保留 / 可简化 / 疑似掩盖错误 / 尚需验证。
3. 为 NC-01、NC-02 补充“依赖暂时失败”和“内部协议缺陷”对照测试，确认原行为和预期行为。
4. 提交按模块拆分的变更计划，不进行横跨仓库的大规模一次性重写。

### P1：小批量收敛异常边界

1. 从可定位且影响较大的 NC-01、NC-02 开始，限定每次改动的责任边界。
2. 随后处理 MA-01、NC-03，优先补可观测性与故障升级，不引入新的通用异常框架。
3. 每个变更说明：删掉了哪条冗余路径、保留哪个不变量、错误现在由谁处理、哪些行为可重试。

### P2：简化控制流与去重

1. 优先处理重复实现、重复校验、无意义代理函数、过度配置项和隐式回退。
2. 保持模块间契约稳定；若必须破坏契约，先同步修改调用方及回归测试。
3. 对缩减前后行数、分支数量、错误类型数量、调用层级和定位效率作实证比较；数字是辅助指标，不应替代正确性。

### P3：谨慎归档遗留路径

1. 根据真实可达性与构建清单而非直觉确定候选。
2. 在安全恢复、迁移、运行路径被证实之后，再做独立提交归档/删除。
3. 生产切换、冷数据剥离和高风险权限变更继续遵守原有门禁，不因“瘦身”自动获得授权。

## 7. 验收标准

- 同类预期故障使用一致、可识别的错误契约；违反内部不变量时不会被转换为看似正常的空结果。
- 可恢复与不可恢复故障在测试中分别验证；有限重试有明确边界，禁止对不确定副作用盲目重放。
- 数据完整性、幂等性、持久化、审批、最小权限、归档撤销、限界读取及故障关闭行为与原基线一致或更严格。
- 失败能被定位：至少包含错误类型、责任模块、原因链和状态；不得泄露敏感正文、密钥或授权凭据。
- 所有修改均提供最小失败复现、回归测试与单独回滚方案；删除遗留模块前证明其不在活跃执行链上。
- 经代码审查确认复杂度确实下降，而不是把处理逻辑搬到另一层或引入更大的兜底框架。
