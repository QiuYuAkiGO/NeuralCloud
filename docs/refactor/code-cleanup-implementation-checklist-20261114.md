## 5. 功能一致性如何验证

### 5.1 三类断言分开

1. **正常功能等价**：固定时间、随机 ID、配置、模型/渠道响应和初始数据库，在基线与清理版各运行一遍。比较 API/工具输出、消息正文、发送次数、落库记录、活动/审批/投递状态、revision/generation、游标及召回排序。只排除事先列明的非业务字段（如执行耗时）；不能泛化删除全部 ID/时间掩盖差异。
2. **不变量始终成立**：事务失败无 DURABLE；相同事件不重复生效；同键不同体拒绝；审批不能二次消费；WAIT 零发送；UNKNOWN 不盲重发；撤销内容不可读；持久化屏障前不推进消费游标。用故障注入和实际 SQLite/子进程恢复验证，不能只 mock 返回成功。
3. **有意改变的失败语义**：非法 JSON/401 从 CACHE_MISS 改为明确错误，或 timer 死亡从 RUNNING 改为故障，是需求要求的差异。PR 单列旧行为、新行为、受影响调用者和测试；不把它包装成“完全行为不变”。错误消息对管理可诊断，对角色/公共响应不包含密钥和私密正文。

- [ ] 不修改固定样本来迁就实现，不删失败测试。已有失败与新增回归分别列出。

## 6. “人类 24 小时上手”的验收

以 24 小时有效学习/操作时间计，允许分多天完成。由未参与实现的人执行，记录实际耗时、打开的文件、依赖他人解释的次数和卡点；开发者不能靠口头补充绕过文档缺口。

| 时间预算 | 新人应完成的任务 | 验收产物 |
| --- | --- | --- |
| 0–2h | 阅读一页系统图，识别三个拥有者、当前/遗留边界、四个常用命令入口 | 能解释“谁写状态、谁写记忆、谁执行工具、谁确认发送” |
| 2–5h | 建立隔离环境，运行默认测试和 TCP 演示 | 可重现命令和结果，完全不依赖生产凭据 |
| 5–9h | 追踪一条 QQ 入站→session 持久化→工具→投递→记忆链 | 标注入口、每次持久化和回执；能解释 WAIT/UNKNOWN |
| 9–12h | 追踪召回、更正失效、临时视图撤销 | 状态归属表与查询链；能解释空结果与不可用的区别 |
| 12–16h | 注入 401、ACK 丢失、timer 故障三个问题 | 从管理状态/日志定位到拥有者，说明哪些可重试、哪些须对账 |
| 16–21h | 完成一个不改协议/权限的小修改，例如增加已定义故障的诊断字段或提取纯校验函数 | 小 diff、相关测试、差分验证；没有添加第二个异常兜底层 |
| 21–24h | 给另一人做代码导览，并自行写出 PR 风险/回滚说明 | 能独立说明变更链与不变量；评审者据文档复核 |

最终通过条件：以上任务在预算内完成，无作者持续带教；常见故障能在给定操作 ID 后 15 分钟内定位到责任模块；正常主链无需阅读 legacy；每个主要副作用的持久化点和重试拥有者都能说清楚。15 分钟是拟定验收目标，尚无实测。未通过则先修入口文档、命名和模块边界，不追加抽象层。

建议随清理交付四份短文档：当前架构/阅读路线、状态与数据所有权、错误与恢复表、开发验证命令。历史研究与生产记录保留原位，通过明确的历史索引访问。
