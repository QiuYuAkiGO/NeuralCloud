# UI 快照读取热修复

共享数据库启用 WAL 后，完整 UI 快照仍出现约 10.9 秒响应和 15 秒超时。独立性能分析定位到 `CognitiveSharedMemory.ui → SharedMemoryStore.query`：每次刷新完整解码约 1.8 万条记录、重复打开注意力策略数据库约 1.78 万次。一次带性能采样的读取耗时 6.62 秒，其中来源校验约 3.15 秒、逐记录策略查询约 2.54 秒。并发浏览器请求还会重复执行同样的工作。

新建仅用于操作者界面的 `operator_recent`：SQLite 扫描排序和可见性元数据，按真实时间及原有稳定排序选取最近 50 条，然后在同一读事务内完整校验这些来源。群策略按不同群检查，并在返回前核对持久化策略版本。记录数是可见性元数据统计，不代表已经重新审计全部历史正文。模型检索仍使用原有完整校验路径。没有数据库结构迁移，也没有跳过展示来源的绑定校验。

Legacy UI 的共享记忆部分作为可丢弃的内存热数据：后台线程异步读取，每个 Cognitive 进程同时最多一个刷新任务。请求取消不会取消后台任务或产生第二个扫描；通常每 2 秒按需刷新，冷读取最多等待 250 毫秒。刷新时可显示上次结果，但年龄超过 15 秒就隐藏；失败清除缓存，错误只记录类型。其余 UI 状态照常返回。返回值包含采样时间、年龄、刷新状态及耗时；界面显示更新时间，读取中或失败时每 2 秒自动重试。

角色、记忆实例或群策略版本改变立即使缓存失效。策略读取失败时不返回旧记忆，旧后台任务也不能覆盖新角色的结果。缓存不会持久化，不回写权威数据库，不进入模型上下文，不产生认知工作或心理收益。Production 模式保留其原有有限条数的即时读取，确保认识撤销和有效期检查继续实时执行。

冻结的 18,216 条真实记录上，新旧上下文及展示内容逐字段一致；旧查询耗时 4,987.6 毫秒，候选三次为 115.5–119.9 毫秒。第一版 `20261007-ui-snapshot-hot-v1`（`bdc7c58`）已部署并验证，但完整 HTTP 测试只通过 8/14 个请求，8 路并发中 6 个超过 5 秒，不能据查询加速宣称完整 UI 已修好。

第二轮定位到 `chat.status → presets_payload → list_summaries` 在事件循环同步读取并校验约 66 MB 角色存档，独立采样耗时 1.27 秒，重复请求串行阻塞，也推迟后台记忆读取。QQ 记忆只读统计还会深拷贝整份历史状态。

第二版将角色列表也放入独立的异步单次刷新缓存，5 秒按需刷新、30 秒最大年龄，冷读取立即返回加载状态；角色列表存档只保留少量摘要缓存，文件身份、修改时间或大小改变后重新校验，外部替换和恢复均失效。当前角色和打开状态仍从实时所有者读取，缓存不复用旧的活动标记。只读 QQ 聚合统计从当前已提交状态计算，显式详情接口继续返回深拷贝，避免调用者修改原始状态。
