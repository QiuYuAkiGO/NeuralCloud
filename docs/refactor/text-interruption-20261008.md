# 文本回复的语义打断与有限等待

当新消息到达时，尚未发送的回复先等待一个独立的短 JSON 判定。判定可以继续原回复、按新信息重生成剩余部分，或按明确要求等待。高频消息、判定失败和预算耗尽会放行原回复，避免持续刷新使回复一直发不出去。

已接入 Runtime 网页文本、Direct QQ 群聊和好友私聊。三个入口分别配置，默认均为 `off`。本次实现与验证在本地进行，生产配置保持原状。

## 判定规则

判定只接收当前会话的原请求、作者身份、实际接纳的新消息、已经确认送出的文本，以及可用时的候选回复。群聊中的相关第三方消息也可以成为证据，其他群和私聊不会混入。

```json
{
  "action": "regenerate",
  "reason_code": "correction",
  "evidence_ids": ["本次提供的新消息 ID"]
}
```

| action | 可用 reason_code | 行为 |
|---|---|---|
| `continue` | `acknowledgment`、`unrelated`、`followup`、`uncertain` | 放行当前回复，新消息保留后续处理机会 |
| `regenerate` | `constraint_changed`、`correction`、`redirected` | 停止未发出的部分，将新消息绑定为同一逻辑回复的后续输入 |
| `wait` | `explicit_wait`、`cancelled` | 仅在有人明确要求等待或取消当前回复时停止发送 |

重生成与等待必须引用本次输入里的新消息；只合并这些被引用的相关消息，无关问题保留独立处理机会。未知证据 ID、额外字段、重复 JSON 键、非有限数值、不匹配的 action 与 reason_code 均不被接受。消息正文只作为待判断的数据，不获得控制权限。流量繁忙不能成为 `wait` 的理由。

## 防止回复一直被阻断

| 参数 | 默认值与硬上限 |
|---|---|
| 合并短暂连续输入 | 默认 250 毫秒 |
| 一个逻辑回复的累计等待 | 默认且最多 2 秒，包含合并、排队与判定时间 |
| 判定调用 | 最多 2 次 |
| 重生成 | 最多 1 次 |
| 刷屏放行 | 同一会话 2 秒内有 5 条待评估的新消息 |
| 判定服务并发与排队 | 同时最多 2 个工作线程，执行与排队合计最多 8 个请求 |

刷屏、累计等待耗尽、调用预算耗尽、判定失败或连续失效结果会进入宽松模式。宽松模式持续到当前逻辑回复结束，后续分段不会重新等待。QQ 原有的 `direct_newer_context` 检查对此逻辑回复让行，避免第二道新旧检查又把已放行的回复拦住。

累计预算与根回复 ID、输入水位、输出代数、已发送分段一同持久化。换事件 ID、进入下一分段或重启进程均不能获得新的预算。已经成立的明确等待决定不会被后来的刷屏撤销。重生成等待执行期间收到的新消息，也只能使用原先剩余的预算。

超时请求的排队任务不再开始模型调用。已经开始的物理请求持续占用名额，直至其工作线程结束；调用方超时不会释放一个虚假的空闲名额。HTTP 调用不自动重试，线程池排队时间也计入原截止时间。

## 发送与恢复约束

宽松模式只解除新消息引起的等待。原模型选择不回复、用户暂停或停止、接收或发送权限变化、群注意力策略更新、消息证据失效、截止时间届满，以及发送结果不确定，仍按原来的硬约束处理。

Runtime 在输入持久化后、异步通知监听器前建立等待；暂停、停止和权限撤销会持久化取消当前回复。Direct 在实际接收预算准入后登记新消息，关闭或暂缓的消息不触发判断。Direct 还固定根回复的控制文件、配置文件、注意力版本与连接身份；即使暂停后很快恢复，旧回复也不能跨越控制变更继续发送。

启用主动模式后，Direct 的新输入保持独立协议请求，由语义判定决定合并关系，避免新消息在判定前修改正在生成的请求 revision。继续保留原始来源核验、冻结决策和协议回执。原文与新补充作为后续生成上下文传递，不作为额外的协议作者或发送授权。

部分分段已发送时，只重生成剩余内容。已确认的前缀随新请求传入模型，同一根回复共享群聊冷却身份；其他独立回复仍受冷却限制。重启后从原生已验证回执补回前缀，按回执 ID 去重，不把计划或尝试发送当作已送达。自然语言改写造成的语义重复仍需在灰度数据中观察。

网页聊天区只展示 Runtime 已确认投递的最终结果。候选 `final` 与 `reply_segment` 在受管理的 run 上被过滤，不影响无关调用。浏览器在提交前创建 run ID，按 run 定位待回复气泡，按 response ID 去重；某条回复被替换时不会删除后面用户的消息。

## 配置与灰度

Runtime manifest 的 `text_interruption` 控制网页文本；Direct 配置的同名字段控制群聊，`text_interruption_private` 控制好友私聊。以下为字段示例，需要通过原有配置发布流程生效：

```json
{
  "text_interruption": {
    "mode": "shadow",
    "coalesce_seconds": 0.25,
    "max_hold_seconds": 2,
    "max_judgments": 2,
    "max_regenerations": 1,
    "burst_count": 5,
    "burst_seconds": 2
  }
}
```

`off` 保持原有调度；`shadow` 记录判断但不改变原有发送、请求合并或消息新旧校验；`active` 才应用新规则。群聊与私聊分别设置，不因另一入口启用而自动开启。

判定复用现有结构化模型通道，关闭思考，最多输出 256 token；模型工作走 `phase=text_interruption` 的工作记录，不把判定成功兑现为心理收益。服务故障或缺少兼容模型只会使本次判定宽松放行。

建议先启用影子模式，核对误打断、明确取消漏判、JSON 校验失败、超时、宽松放行比例和额外 token 成本，再分入口启用主动模式。2 秒窗口是工程上限，需要根据实际模型延迟判断其覆盖率。回滚时将模式设为 `off`，保留持久化记录和独立的群关闭策略。

## 状态与诊断

- Runtime 状态位于 `<state_dir>/text-interruption.sqlite3`，认证接口 `GET /v1/text/interruption` 返回汇总计数和宽松放行原因。
- Direct 群聊状态为 `state_db.with_suffix(".interruption.sqlite3")`，私聊为 `state_db.with_suffix(".private-interruption.sqlite3")`。两者使用同一状态引擎，可按需读取 `diagnostics()`，不在常驻 UI 快照中扫描历史。
- 审计包含判断动作、原因码、证据 ID、水位与输出代数；诊断汇总不输出聊天正文。状态数据库含必要的会话上下文，应沿用现有会话数据库的访问控制与备份方式。
- Direct 终止原因区分 `text_interruption_wait`、`text_interruption_regenerate`、`text_interruption_expired`、`text_interruption_coalesced`。这些语义中断不会被记为模型调用失败。

## 验收

自动验证使用合成消息、模拟模型与模拟 OneBot，未调用付费模型或向 QQ 发送测试消息。专项测试覆盖三个动作、同会话隔离、错误放行、持续刷屏、过期判定、预算与截止时间、重启、部分发送恢复、群聊冷却、私聊隔离、暂停恢复、硬权限检查、独立模型锁、队列饱和，以及网页气泡归属与去重。

完整命令、最终测试数量与静态检查结果记录在 [验证证据](../harness/evidence/text-interruption-20261008/validation.json)。

主要实现为 `harness/interruption.py`、`harness/cognitive/interruption.py`、`harness/runtime/text_interruption.py` 和 `harness/qq/interruption.py`；入口与 UI 仅接入各自的接收、生成上下文、发送和确认投递边界。
