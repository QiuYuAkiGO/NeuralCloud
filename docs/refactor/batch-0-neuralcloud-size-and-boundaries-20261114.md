## 1. 结论先行

1. 最新实施分支有 **278,917 行源码类文件**，其中 **247,373 行非空**。不是上一轮提到的约 2,000 行：2,038 行仅是新 Python 记忆包。
2. 默认构建/测试选中的记忆实现，加上手机插件，共 **3,530 行**；再加尚需核实部署归属的 QQ 桥接和口语工具，共 **5,093 行**。这两个数字包含相应测试和工具，不是全仓代码。
3. 目前没有证据承诺全仓能安全缩减到几千行。**不归档旧实现时，全仓仍约 27.9 万行；完成依赖确认、恢复验证和归档后，日常维护源码暂估约 4,000–8,500 行。** 后一个区间是有条件的规划，不是已经证明可删除 97% 代码。
4. 当前新记忆主包的 10 个文件划分基本合理，应优先清楚标出在线、管理、迁移三个边界；不必把 2,038 行再拆成大量包。更大的问题是手机通讯、Misty 表达部署、旧运行系统和记忆服务混在同仓，但不在同一构建/测试门禁下。
5. 清理成功应体现为“新人只需先读约 1,000–1,500 行主链即可解释日常操作”，而不是全仓代码必须减少某个百分比。显式错误处理、故障测试和展开压缩代码可能增加行数。

### 5.1 新 Python 包：合理，先标明边界，不继续细碎拆分

| 逻辑模块 | 当前文件/行数 | 职责及建议 |

| 历史迁移 | `migration` **428** | 离线命令、只读源、分批游标。把 108 行 step 按读取/转换/提交提取具名函数即可；不引入新服务 |

建议依赖方向保持：`CLI/API → storage → contracts/ownership`，`maintenance/temporary_views → archive → storage`，`migration → storage`；角色 API 不反向导入管理/迁移。插件只通过 HTTP/SessionStore 契约接入，手机插件不直接访问记忆 DB。

日常理解路径为在线 684 + 记忆插件 155 + 手机 188 = **1,027 行**（不含生成声明）。归档/迁移按任务再读 1,354 行；新人不用先读所有旧运行时。清理后把这一必读主链预算设在约 1,000–1,500 行，比限制全仓总行数更接近 24 小时目标。

### 5.2 整个仓库：所有权与导航尚不合理

- **入口冲突**：根部启动脚本指向旧 GUI；README 指向 resident CLI。新用户存在走错架构的风险。先给所有入口注明当前/旧版/维护用途；未证实退役前不删除。
- **部署源与领域归属不一致**：Misty 的表达补丁放在 NC 的 tools 中。应建立唯一源文件与发布配方映射；表达逻辑宜由 Misty/Harness 拥有，NC 保留历史证据链接。不能复制两套新源文件。
- **测试边界漏口**：手机插件有可安装入口，但未进入当前 CI；QQ 桥接及口语工具也不在 resident 门禁中。应为每个保留入口绑定测试，不能用 28 项记忆测试证明整仓功能。
- **历史资料污染阅读面**：研究数据、tokenizer、源码快照、旧测试大量占据默认树。先隔离导航和模块状态，后决定是否从默认树迁出；审计、恢复的 hash/引用需要保留。
- **不需要新的微服务**：记忆在线、归档、迁移共享数据不变量，逻辑分区已经足够。增加服务只会引入跨进程事务和更多错误分支，违背降低复杂度目标。
