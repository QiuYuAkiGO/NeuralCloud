01 · 对这次重设计最有影响的证据

建议先实现一个容易击败、也容易解释的基线。
原始轮次或小事件窗口保留完整文本；SQL 管身份、权限、时间和版本；词法与向量检索形成候选。只有相对该基线带来可重复收益的记忆加工步骤，才进入默认路径。这个选择是结合文献和项目目标作出的工程判断。

构建复杂记忆并不保证更好

独立复现 · 2026-07LightMem 复现研究固定记忆库和回答模型后，仅更换检索器，答案准确率便从 58.1% 变化到 75.5%。原始对话检索在相同 top-k 下通常更强；压缩记忆主要在紧张的回答上下文预算下有优势。它在 LongMemEval-S 的 444 题子集上测试，排除了 56 道 assistant 记忆题，不能外推为所有记忆任务的结论。[R1：§3–6]

把成本移到后台不等于成本消失

LightMem 将合并更新移到离线阶段，适合降低交互阻塞；Neuromem 则把插入和查询交错评测，发现压缩和生成式整合常在写入、读取之间转移成本。我们必须同时统计后台 token、队列滞后、重建与尾延迟。[R2] [R3]

03 · 物理存储应服务于最小数据模型

设计判断建议保留一个权威记忆提交边界。原始渠道数据库可以继续存在，但导入后的来源身份、版本和派生关系应有统一定义。语义类型不必各建一个数据库或一套 worker。

组织/存储方式适合保存主要取舍本次建议
追加事件 + 关系数据库原始轮次、作者、会话、事件时间、接收时间、版本、证据引用可精确过滤、事务提交和回放；需要索引与保留策略作为主干，复用已存在的来源账本
文本 / JSON / Markdown 文件人格配置、人工维护规则、离线导出、技能案例可读且便于版本管理；频繁并发更新、跨对象引用和大文件重写更难管理保留配置与导出用途；持续增长的运行记忆逐步改为记录级更新
词法索引 + 向量索引原文片段与派生条目的可重建检索表示词法擅长名字与精确词；向量擅长改写相似度。都不应承担事实真伪和权限判定索引可重建；先复用现有中文 postings，再测试向量增益
摘要层次 / 主题树长事件概述、跨会话主题、压缩后的实体视图节省上下文；更新与多层重汇总有代价，也可能丢失细节先只增加一层可溯源摘要，避免默认递归层次
实体关系图 / 时序图跨人际关系、时间有效区间、关联检索路径需要抽取、消歧、冲突解析和图维护先在 SQL 中保留 source/supersedes/related 引用；有真实多跳缺口再引入图索引

当前项目已有 SQLite 来源与生产记忆存储，也已有 PostgreSQL/pgvector 适配。先按部署负载选择一个权威后端，避免同时迁库与改算法。单机、可串行化写入时优先复用 SQLite；持续多写进程争用时再评估 PostgreSQL。SQLite WAL 支持读写并行，但同时只有一个 writer。[D1]

中文词法索引需要专项验证。FTS5 提供不同 tokenizer，trigram 对短查询有边界；不要把默认分词等同于中文检索已解决。现有中文 bigram/postings 可作为对照，覆盖两字人名、别名、否定和中英混输。[D2]

05 · 最小重设计：来源、视图、索引各司其职

设计提案把数据收敛为两类权威记录：来源事件和带版本的记忆条目。事实、经历、反思是条目的 kind；不是三个独立维护系统。索引和上下文包是派生产物。人格配置与短时情绪状态继续由各自的状态模块管理。

→

来源原文也建立检索入口；异步视图未就绪时仍可召回新事件。逻辑上共用一个提交协议，不要求一次合并所有物理渠道数据库。原则参考 R1/R2/R4/R8/R10；此组合并非任何一篇论文的原样实现。

在线写入
验证来源身份与 audience → 以 source_id 幂等追加 → 同事务写入 outbox/游标 → 更新近期窗口和轻量词法索引。避免等待生成式摘要。新消息先以原文可见；明确的更正事件在视图更新前随旧记录一起交给回答模型。
后台派生
按新增事件窗口处理；先用哈希/规则去重，再按需用一次结构化模型批处理生成候选。冲突、主体不明或高影响的关系变更进入现有严格审查。只提交 delta；来源、版本、回执与索引任务有一致的提交边界。
在线检索
可信身份与受众在评分前过滤 → 近期事件、当前事实、词法/向量候选合并 → 证据 ID 去重 → 按时间和适用范围回源 → 按 token 预算组装。保持一次有界召回；同一来源的摘要与原文不算两份独立证据。
维护与遗忘
默认淘汰缓存/索引中的低价值表示，避免每次命中触发模型维护。事实过期采用有效期与 supersedes；原文按单独保留策略处理。真正删除时同步撤销派生条目和索引，保留最小 tombstone 防止回放复活。

例如“去年住杭州，现在搬到苏州”应保存两个带时间与来源的记录，并形成当前住所视图；“她最近可能在疏远我”保留为主观解释，不能覆盖客观经历。检索相似度、出现次数和重复总结都不自动提高事实可信度。借鉴 Zep 的时间区分与 Hindsight 的证据/推断分离即可，不必完整引入它们的网络结构。[R8] [R10]

按问题增加工作量，而不是每轮运行完整流程

普通路径目标为 0 次生成式记忆管理调用；embedding 编码单独计费、计时，不能藏进“0 次模型调用”。路径选择初期使用确定性条件；只有规则达不到要求时才研究学习式路由。

明确从默认路径里移除什么

  • 每条消息的多轮抽取、合并、反思：改为窗口级候选处理；必要的高影响审核仍保留。
  • 每轮全历史装载、重建投影或整份大快照持久化：改为游标、增量提交与受影响项失效。
  • 重复管理同一事实的多条写入管线：统一提交协议和来源身份；QQ、daily revision 等成为调用者。
  • 无证据增益的多层摘要、全图演化和普遍反向检索：保留为实验或按需功能，必须带来可测收益。

保留来源链、会话/受众隔离、有效期、幂等性、恢复与撤销。这些能力决定记忆是否可靠，不宜通过删除它们来获得表面上的代码减少。

06 · 用消融决定功能，用全生命周期成本决定架构

先从当前实际配置取得基线。在相同回答模型、embedding 版本、上下文预算、硬件和并发下比较；固定 judge 并抽样人工复核。按会话与时间隔离调参集和测试集，所有题只能使用问题发生时已经出现的证据。

方案变化回答的问题
A · 当前系统冻结配置与源码；测真实启用分支成本究竟来自导入、查询、锁等待、模型还是保存？
B · 原文强检索来源轮次/事件窗口 + 身份/时间过滤 + 词法和向量消融 + 同预算上下文移除生成式记忆构建后损失多少？纯词法与混合检索各有何缺口？
C · B + 一层派生记忆增量事实/摘要，统一版本与证据，不引入递归图压缩是否值得其写入与维护成本？
D · C + 按需深度回忆仅在跨事件题上做一次额外扩展或证据组织能否以少量慢请求补足长程推理？

质量与可靠性

  • 证据 recall@k、答案正确率、无证据时的恰当拒答。
  • 人名/别名、跨群同名、否定、时间范围、事实更正与来源撤销。
  • 跨会话共同经历、承诺与关系变化；抽样评估角色自然使用记忆的质量。
  • 误归因、跨受众泄露、把模型推断当事实的发生率。
  • 区分“原文已保存但未召回”和“加工时已丢失”，通过原文/派生 oracle 对照定位。

成本与系统行为

  • 追加、首次可检索、派生就绪分别统计 p50/p95/p99；与首 token/总回复时间分开。
  • 每千条输入的生成式调用数、embedding 数、输入/输出 token，以及后台总成本。
  • 候选解码行数、锁等待、写放大、存储量、重启恢复与索引重建时间。
  • 后台任务积压及其对前台尾延迟的影响；测试读写交错和并发。
  • 在 1千 / 1万 / 10万条事件规模下测增长趋势；这些是建议测试点，不是已测容量。

总成本 = 初始构建 + 增量写入/合并 + 查询/生成 + 后台维护 + 恢复/重建

只有预计查询量 × 每次读取节约成本，大于构建、维护和重建的额外成本时，预先压缩才在成本上值得做；同时还要满足质量与新鲜度约束。延迟要分别按关键路径评估，不能把 token 减少直接换算成响应提速。

基准组合

LongMemEval 覆盖更新、时间推理、多会话和拒答；LoCoMo 适合长对话与事件回顾；MemoryAgentBench 补充增量输入、学习与选择性遗忘。它们都不能替代中文角色对话、QQ 权限范围与生产队列的本地验证。建议另建约 200 条分层标注查询，先做小样本试验，再决定扩展规模。

建议验收门槛与迁移顺序

提议值 · 待基线校准主要质量指标下降不超过 2 个百分点；记忆子系统 p95 至少下降 30%；全生命周期模型 token 至少下降 50%；受众隔离、来源验证、更正和崩溃恢复的关键用例全部通过。若基线已几乎没有生成式记忆开销，则改用写放大与维护项数量评价，不能强行套用 token 目标。

  1. 测量：记录当前启用配置、读写频率和各阶段 trace，建立 A/B 基线。
  2. 先收敛接口：原有调用者通过同一来源/版本/提交协议，保留旧数据与回滚入口。
  3. 影子验证：从快照与增量日志生成候选视图；对同一查询做离线比较，不形成第二套可独立写入的真相。
  4. 分阶段切换：先切读路径，再切写入权威；可校验回放和恢复后退役旧投影/worker 分支。暂时双读须有明确结束条件。
