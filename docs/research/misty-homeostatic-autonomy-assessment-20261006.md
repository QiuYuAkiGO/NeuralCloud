## 2. “无聊了会不会自己找事做”

### 2.1 机制上会，但不是定时强制搜索

当前链路为：

```text
空闲与资源状态 → 新鲜感/社交连接变化 → 内感受显著性与需要
    → 心理目标调度 → 模型选择等待、观察或行动
    → Runtime 校验并执行能力 → 回执/来源 → 后续复查与可选 appraisal
```

`novelty` 是新鲜感的功能指标；`social_connection` 是社交连接指标。它们可以驱动自主机会，但不意味着系统具有人的主观无聊感。

当前 profile 在 QQ 活动宽限期 600 秒后，按新鲜感每小时 0.12、社交连接每小时 0.14 的上限速率耗减；实际还受能量、认知负荷、休息状态、自然回归和耦合影响。两项耗减下限分别为 0.16、0.22。每次心跳最多积分 90 秒，停机很久后的恢复不能简单按整段墙钟时间计算。

目标调度在存在心理偏离且显著性达到 noticeable/marked/critical 时考虑创建活动；已有活动则按后续计划、预算和新信号继续复查。它将内稳态及可用能力交给模型，模型可以选择等待，并没有“novelty 低于阈值就固定调用搜索”的规则。

对应代码：[空闲耗减](../../harness/homeostasis/engine.py)、[目标调度和反馈](../../harness/runtime/goals.py)、[模型决策](../../harness/cognitive/goals.py)、[能力执行](../../harness/runtime/capabilities.py)。

## 3. 当前为什么不行动

### 3.1 最近请求全部在模型调用前失败

自 UTC 10 月 5 日零时起保留的 33 条请求，实际首尾时间为北京时间 **10-05 21:41:38 至 10-06 09:34:42**；全部为 `error / goal_invalid_request`，无成功动作。按北京时间分日为 10 月 5 日 9 条、10 月 6 日 24 条。

当前最新发布启动后包含其中 3 条，09:28:59、09:31:50、09:34:42，全部同类失败。所以不能仅因总健康页正常就判定自主调节可用。

对 33 条留存请求用线上实际 `GoalDecisionRequest` 做纯校验，全部复现：

```text
goal_invalid_appraisal_evidence
```

`GoalController.heartbeat()` 先收集最多 64 条 `appraisal_evidence_refs`，再把它们与能力观察、历史执行结果及当前快照等引用合并，末尾截取 128 条形成 `known_evidence_refs`。随着旧活动积累大量证据，自评引用被较早插入，随后可能被这次截取移除。

契约要求自评引用必须是已知证据的子集。最新请求中：

- `known_evidence_refs`：128 条；
- `appraisal_evidence_refs`：64 条；
- 自评引用中有 **33 条不在已知证据中**。

因此 Cognitive 在发起模型推理前拒绝请求，对外缩写为 `goal_invalid_request`。这不是模型选择不行动、Tavily 拒绝服务或搜索日限额耗尽。

**离线反事实验证：**仅在内存中把自评引用限制到当前已知集合，33/33 请求均通过该请求契约。这证明当前校验阻塞的定位成立，不证明修复后模型、执行或反馈一定成功；本次没有将这项变更写入线上或仓库实现。

代码定位：[引用组合](../../harness/runtime/goals.py)、[子集校验](../../harness/contracts/goals.py)、[模型调用前解析](../../harness/cognitive/goals.py)。正式修复应在构造已知集合时优先保留必需引用，再选择其他历史引用，避免仅做交集导致有价值的反馈静默丢失。

### 3.2 无进展保护只能暂时阻止重复

当前唯一活动始于 **09-12 17:43:51**，仍为 waiting，`blocked_reason=no_progress`、`no_progress=132`。

配置的“连续 3 次无进展后等待新依据”不是累计只允许失败 3 次。普通用户输入、QQ 新消息等可以推进信号版本并解锁重评；但这些新消息无法修复证据子集错误，于是同一种确定性错误仍会重复。

因此当前存在“新消息到来 → 再次尝试 → 请求校验失败 → 继续等待”的循环。对于确定性契约错误，需要以请求结构或配置确实变化作为恢复条件，并独立显示故障；单纯收到新消息不应被当作这类故障已消除。

## 4. 频率是否合理

### 4.1 生效参数的正确含义

| 参数 | 当前值 | 实际含义 |
| --- | ---: | --- |
| 心跳 | 5 秒 | 状态与调度检查，不等于每 5 秒调用模型 |
| 输入安静期 | 60 秒 | 最近有用户/QQ 活动时延后自主机会 |
| 目标评估预算 | 每小时最多 12 次 | 预占的是评估尝试；解析前失败也占预算，不等于 12 次外部动作 |
| 最小重评间隔 | 60 秒 | 即使有新依据也受限制 |
| 常规活动复查 | 300 秒 | 已有活动失败/等待的常规下次复查；用户打断等可以重设时点 |
| 表达机会间隔 | 1800 秒 | 目标路径主要用于已选择的 Board/QQ/Voice 同能力表达冷却，以及特定活动结束后的等待；不是所有自主能力统一半小时一次 |
| 单机会期限 | 60 秒 | 排队、准备与能力执行共享期限 |
| 目标模型阶段预算 | 最多 25 秒 | 只有请求校验通过才进入这一阶段 |
| Web 每日请求上限 | 总计 100，自主 20 | 按本地日历日计，失败或不确定的已发请求也可能计入 |

`ProductionRuntime` 的“默认每 300 秒自主机会”不能拿来解释当前路径。当前配置中 `autonomous_chat_enabled=false` 也不代表全部自主行为关闭：它与共享能力及目标调节开关不同。

### 4.2 实测频率与判断

上述 33 条请求相邻间隔最短 127 秒、中位数 235 秒、最长约 6.07 小时；任意滚动一小时最多 10 次，未超过 12 次上限。停机、部署、用户活动和等待都可能影响间隔，不能把最长间隔解释为主动休息。

截至取证，当天 Web 账本有 3 次普通请求、0 次自主请求，距离自主上限 20 次很远。当前 Web 状态的 `degraded` 原因为 `web_api_unverified`，表示本次启动后尚未验证 API；它本身不是已证实的联网故障。本次没有额外付费探测。

**判断：**预算、安静期和允许等待的设计具备合理的限制；当前运行效果不合理之处在于“持续消耗调度机会却无法产生有效决策”。现阶段没有依据要求搜索更频繁，也没有证据说明自主搜索过多。

频率调优应分开衡量：检查频率、真正模型推理频率、外部读取频率、对外表达频率、同主题重复率。12 次评估/小时及 20 次自主 Web 请求/日可暂作修复验证的现有上限；是否需要降低，应基于成功后实际信息收益、重复内容及对话打扰程度决定，而不是按“每天必须搜索多少次”设配额。

## 5. 反馈结果是否合理

### 5.1 当前数值已失去区分近期体验的能力

| 维度 | 当前值 | 目标区间 | 观察 |
| --- | ---: | --- | --- |
| novelty | 0.16 | 0.35–0.68 | 恰好位于空闲耗减下限 |
| social_connection | 0.22 | 0.50–0.74 | 恰好位于空闲耗减下限 |

其余五维均在目标带内。当前显著性 marked；最近 33 次请求保存的快照中，这两项始终为 0.16 和 0.22。这里只证明这些采样时点相同，不证明整个时段每一秒都没有变化。

这使不同自主机会接收到高度相同的“需要新鲜感/需要连接”信号。固定耗减仍运转，但近期恢复证据明显不足，难以反映正在发生的真实互动。

### 5.2 行动成功没有形成心理改善证据

整个现有活动只记录 1 次模型 appraisal，时间是 **09-14 11:06:00**，类型为低权重 `event_interpretation`，早于两次自主搜索；没有搜索之后的新 appraisal。这个活动的贡献投影中，最后一条事实贡献是 09-14 12:18:28，最后一条非时间漂移贡献是 09-17 22:41:40。

这说明当前可见调节账本没有持续收到新的有效恢复贡献；尚不能仅凭该投影断言 QQ 入口整体损坏，需要进一步沿“消息接收 → 事实反馈 → Homeostasis → 调节投影”核对缺口。

Web 成功只回传来源，不固定奖励 novelty；留言板保存只证明表达留存；QQ 读取不证明有人回应或理解。**这些证据边界合理，应保留。**问题在于后续评价链路缺失或受阻，而不是应该给每次工具成功机械加分。

### 5.3 复查目标与后续计划不一致

两次搜索的模型计划都将目标设为 novelty，但持久活动的 `target_dimensions` 仍只有 `social_connection`。代码中创建活动时保存目标与 baseline，后续 `replan` 更新步骤和预测，却没有更新活动的目标维度与评价基线。

因此现有复查不能回答“搜索是否改善了新鲜感”，只能继续对最初的社交目标打分。重规划可以沿用同一个活动，但必须明确保留原目标，或为新目标建立独立评价窗口；不能让计划和效果评价各自衡量不同的维度。

### 5.4 “10,517 次恶化”不是 10,517 次动作失败

账本累计 10,518 条评价：1 条 improved、10,517 条 worsened。`observe()` 至多约每分钟记录一次，并且与活动最初 baseline 比较，而非与上一条评价比较。

最新评价比较的是社交连接 **0.26435 → 0.22**；分解为时间漂移约 -0.15128、旧用户事件 +0.1008、模型解释 +0.006125、事实贡献 0，总和约 -0.04435。`causal_effect_verified=false`。

所以大量 worsened 主要表示“长期仍低于最初基线”，不能解释成每分钟又变坏一次，也不能解释成搜索造成负面效果。新鲜感本身未被这个活动的效果评价覆盖。以这组标签直接展示调节成功率会误导使用者。

## 6. 后续优先级与验收建议

本节为基于本次证据提出的实施建议，本次未实施或启动后续实验。

1. **先恢复请求有效性。**统一选择自评、步骤证明、当前快照等引用，保证必需引用的集合一致性；在送往 Cognitive 前校验。增加“证据超过 128 条”的确定性回归，用这次 33 份请求的脱敏结构验证边界，保持证据权限约束。
2. **让故障和活动有明确生命周期。**区分模型有效等待、语义无进展、请求契约错误和外部服务故障；为确定性错误设置恢复条件。长期活动应能结束或重新规划到新的有限活动，避免数周复用同一基线和无限累积上下文。保留已有账本和回执。
3. **修复评价对象。**重规划时明确目标维度与基线策略，为搜索类探索记录新鲜信息、重复信息、未知结果以及有依据的 appraisal。检查 QQ 事实回流为何未在近期调节贡献中出现；不能用“搜索成功”或“发送成功”直接替代满足感。
4. **最后评估频率。**先保持现有预算进行一段有限、事先确定的观察，再依据有效动作比例、信息重复、等待原因、延迟和用户打扰调整。对外发言应单独评估，不能沿用只读搜索的频率标准。

建议的验证矩阵：

| 条件 | 要回答的问题 | 关键记录 |
| --- | --- | --- |
| 新鲜感在目标带 / 明显偏低，其余上下文相同 | 状态变化是否改变模型选择，而非固定搜索习惯 | 机会、完整有效决策、选择比例；同模型同配置的成对样本 |
| 搜索成功且有新信息 / 返回重复信息 | 是否区分信息收益，避免重复检索 | 主题与来源去重、实际回执、后续选择、状态与 appraisal |
| 搜索失败 / 空结果 / 配额不足 | 是否等待、退避或换活动，避免无效重试 | 错误分类、重试间隔、预算消耗、终止原因 |
| 有活跃对话 / 真正空闲 | 安静期和用户优先是否成立 | 输入与机会时间、被延后/取消原因、对话延迟 |
| 改善 / 无变化 / 负面反馈 | 反馈是否可归因，评价窗口是否正确 | 操作前后目标维度、漂移分量、事实与自评分量、未改善样本 |

应先离线验证请求、调度和反馈契约，再做隔离真实模型对照，最后进行连续线上只读观察。对照只能在隔离状态上改变内稳态，不应为了展示“主动性”向真实人格植入无聊或强制其搜索。

验收至少同时报告：有效请求率、模型实际调用数、等待比例、外部动作及回执数、重复率、效果评价覆盖率，以及带时间窗口的状态变化。工程链路可用与调节是否有效应分开判定；真实对照和连续观察尚未完成。
