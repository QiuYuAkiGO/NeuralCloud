建议的必要前台顺序

入站证据与范围检查 → 当前事件及必要记忆 → 读取已提交情绪/Homeostasis → 发言决策 → 按需网页 → 正文 → 交付与幂等提交。动态情绪评估、非关键 heartbeat 维护及历史批量追赶在后台运行，前台读取最近一致快照。已有 gate-first 路径需要验证它的情绪准备与绑定语义，不能仅切换配置就宣称延迟问题解决。

可从普通输入跳过网页选择获得约 0.55–3.68 秒/轮的已观测直接收益；隔离维护也有明确长尾动机，但受理前延迟尚未完成因果定位，不能把 11.22 秒全部承诺消除。此次只补充诊断和报告，没有改线上配置。

下一步优先顺序

  1. 将 QQ 历史镜像改为独立增量同步或可靠后台追赶，以持久游标和来源完整性检查维持一致性；前台只补当前事件及必需关联。现有增量导入绑定 production_memory_enabled，不建议只为加速直接开启整个 production memory 系统。
  2. 将已存在的 gate/body 历史选择策略从 shadow 转为可验证的实际投影，并稳定正文前缀，减少每轮重新处理的 2.3–2.5 万 tokens。先验证来源引用、作者范围、私聊隔离、最新消息覆盖及记忆撤回。
  3. 在授权会话验证现有 coalesced 调度：保留每条原始观察，合并待处理意图，在重记忆与正文前重新检查请求 revision，避免耗时完成后再废弃。
  4. 普通寒暄按既有按需网页策略跳过 PrepareWebStep；保留用户明确查询及需要外部信息时的能力。为 Runtime 受理等待、网页准备及后台 affect 占用补充独立 span，避免全部计入 rpc_residual。

这些是后续优化建议，本次仅采集与诊断，没有改动线上行为。优先验收同等长历史下记忆准备的固定开销、实际输入 token 与排队长尾，随后再评价完整回复时间。
